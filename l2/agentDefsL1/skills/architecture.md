# agentDefsL1 architecture

Hexagonal defs for one module. This file is context for a later materializer.
It does not dispatch `agentCbMaterialize`, and it does not point at a `.d.ts`
that no definition dependency produces. The def file exports `definition` only.
Skills and future output paths are conventions of the materializer, not fields
the model writes.

Dependency direction:

- a registry depends on adapters
- a controller depends on usecases and the access scope
- a usecase depends on ports, domain models and scope
- an adapter depends on its port and its table
- a usecase does not depend on the registry or the adapter

Future `.ts` paths are derived from the def path. They are not generated by
this step and they are not stored on the def. finalize80 records that absence
as pending materialization. It does not publish and it does not start a repair
cycle. A status of `pending` is the D1 default. `generated` is evidence from
the materializer and is kept only when the semantic hash still matches.
